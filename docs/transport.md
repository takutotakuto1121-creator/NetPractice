# トランスポート層
## トランスポート層(レイヤ4)
**トランスポート層**は通信における**信頼性に関するプロトコル群**が定義されている層。
- 確実な伝送かスピードか、どちらを優先するか
- 異常があった時の対処に関するルール
- 送信量の調節に関するルール

など、通信が期待通り行われるためのプロトコルが定義される。
TCP/IPモデルでもトランスポート層で、ここで活躍する代表的なプロトコルが**TCP**と**UDP**。

## ポート番号
IPアドレスは「郵便番号(配達エリア)」にあたり、ホスト(コンピュータ)間の通信を特定する。
1台のコンピュータの中には複数のアプリケーションが動いているため、**どのアプリケーションからどのアプリケーションへ送るか**を特定する「住所」が必要になる。これが**ポート番号**。

- アプリケーションを特定するための番号を**ポート番号**という。
- ポート番号により1台のコンピュータ(1つのIPアドレス)で複数のアプリケーションを同時に利用できる。この機能を**セッションの多重化**といい、トランスポート層が提供するサービスの一つ。
- **送信元ポート⇔宛先ポート間で滞りなく通信を行うために定義されるプロトコル群**がトランスポート層。

例: クライアント(192.168.100.1)のポート50000番・55000番・60000番のアプリが、サーバ(183.181.98.148)のポート20番・25番・80番のアプリとそれぞれ通信する(宛先IP+宛先ポートで荷物に宛名が付くイメージ)。

### ポート番号の範囲
ポート番号は**16ビット**の整数(**0〜65535**)で定義される。

| ポート番号 | 種類 | 詳細 |
| --- | --- | --- |
| 0〜1023 | **ウェルノウンポート** | インターネット標準として管理されている予約済みのポート番号。サーバ側のポートとして使用される。例: SMTP(メールサーバ)は25番 |
| 1024〜49151 | **登録済みポート** | サーバ側で予め登録されているポート番号。例: Microsoft SQL Serverは1433/1434 |
| 49152〜65535 | **ダイナミックポート** | 誰でも自由に使用可能なポート番号。主にクライアント側の送信元ポート番号として使用される |

## TCPとUDP
送信側から受信側へデータを送る時のルールとして、**TCP**と**UDP**がある。

| | TCP | UDP |
| --- | --- | --- |
| 重視するもの | **信頼性**(大切なのは安心感。確実にお届けする) | **スピード**(速さこそ正義。細かいことは気にしない) |
| 特徴 | 確実に届けられるが、時間がかかるため被害(混雑など)は甚大になりうる | 速いが、データが欠損するなどのアクシデントの可能性がある |

## TCP
**TCP**(**Transmission Control Protocol**)はIP同様インターネットにおいて標準的に利用されているプロトコルで、信頼性の高い通信を実現するために使用される。
信頼性を高めるために送信元&宛先双方で状況を確認しあいながら通信する方式を**コネクション型**といい、TCPもその一つである。
送信データは**セグメント**という単位に分割されて制御・送信される。

### TCPの通信の流れ
TCPの通信は大きく**接続**・**データ転送**・**切断**の3段階に分かれる。

| 段階 | 内容 |
| --- | --- |
| 接続 | コネクションの確立(3ウェイハンドシェイク) / 最大データ分割サイズ(MSS)を決定 / シーケンス番号の初期値を決定 |
| データ転送 | セグメントの生成(TCPセグメンテーション) / セグメントの送信(順序制御・確認応答等) / アクシデントへの対応(再送制御) / 送信の効率化(ウィンドウ制御) / 適切な送信量を調整(フロー制御・輻輳制御) |
| 切断 | コネクションの終了 |

### TCPセグメント
**セグメント**は**トランスポート層のPDU**(Protocol Data Unit)。TCPヘッダ+転送データをまとめたものを**TCPセグメント**という。
(復習: PDUはヘッダ(+トレーラ)が付加されたデータ単位。レイヤによって呼び名が変わり、**L2:フレーム、L3:パケット、L4:セグメント**は必ず押さえておく。コリジョンドメインを「セグメント」と呼ぶこともあるが、ここでいうセグメントとは別物。)

TCPヘッダのフォーマット(カッコ内はビット数):
- 送信元ポート(16) / 宛先ポート(16)
- シーケンス番号(32)
- 確認応答番号(ACK番号)(32)
- データオフセット(4) / 予約(6) / **制御ビット**(6) / ウィンドウサイズ(16)
- チェックサム(16) / 緊急ポインタ(16)
- オプション / パディング

ヘッダは大きく「**送信元+宛先ポート番号**」と「**TCPで使用する様々な制御情報**(+α)」に分けられる。

| フィールド | 内容 |
| --- | --- |
| シーケンス番号 | 送信する分割データが元データと比較してどの位置にあるかを示す番号 |
| 確認応答番号(ACK番号) | 受信状況と次に受信したいデータのシーケンス番号を送信元に示す番号 |
| ウィンドウサイズ | 受信可能なバッファ領域の状況を送信元に伝える |
| チェックサム | エラーチェック用 |
| 緊急ポインタ | 緊急で対応が必要なデータの位置を示す |
| オプション | 必要に応じて自由に使用(MSSの通知など) |

### 制御ビット
**URG / ACK / PSH / RST / SYN / FIN**の6ビットで構成されるTCP通信制御に使用されるフィールド。各フィールドに1をセットすることで、対応する制御情報を送信先に伝達できる。

| ビット | 意味 |
| --- | --- |
| **URG**(Urgent Pointer) | 緊急対応が必要 |
| **ACK**(Acknowledgement) | ACK番号が有効(OK!) |
| **PSH**(Push) | 受信後すぐにアプリに渡す(これお急ぎで!) |
| **RST**(Reset) | 異常発生のため強制的に終了したい |
| **SYN**(Synchronize) | 接続開始したい |
| **FIN**(Finish) | 接続切りたい |

**制御ビット(追加)**: 現在は輻輳制御関連で3ビット追加されている。
**NS**(2003年, RFC3540)、**CWR**(Congestion Window Reduced) / **ECE**(Explicit Congestion notification Echo)(2001年, RFC3168)。いずれも元々は予約フィールドの空きを使っている。

## コネクションの確立(3ウェイハンドシェイク)
TCPでは通信前に必ず**コネクション**(接続)を確立するための情報のやり取りを行う。これを**3ウェイハンドシェイク**という。使うのは制御ビットの**SYN**と**ACK**。

### 片方向の接続確立
1. 送信元から宛先に接続したい旨を伝えるため、**SYN:1**にしてセグメントを送信する。
2. SYN:1のセグメントを受け取った宛先は、接続を承認する場合、送信元に**ACK:1**にしてセグメントを送り返す。

これで送信元→宛先の向き(片方向)の接続がOKになる。TCPは双方向で状況を確認し合うため、逆方向の接続も必要。

### 3ウェイハンドシェイク(双方向)
送信元をA、宛先をBとする。
1. A→B: 接続要求を伝えるため、**SYN:1**でセグメントを送信する。
2. B→A: 接続承認 & B→Aの接続要求を伝えるため、**ACK:1 / SYN:1**でセグメントを送り返す。
3. A→B: 接続承認を伝えるため、**ACK:1**でセグメントを更に送り返す。

これで双方向の接続が完了する。

### おまけ:コネクションとセッションの違い
- **セッション**: アプリケーション同士の一連のデータのやり取り(通信そのもの)。
- **コネクション**: 通信ルート(道筋)。セッションより下位の考え方で、コネクションの上でセッションが行われる。

IP電話の例: 電話をかけて相手が出る → コネクションの確立 → 会話(一連のデータの流れ)がセッション → 会話が終わるとセッションの切断 → 電話を切るとコネクションの切断。

## TCPセグメンテーションとMSS
データを送る時、一度に運べる量には限りがあるため、**分割 → 送信 → 再構成**する。これを**順序制御**という。

- **TCPセグメンテーション**: 分割すること(トランスポート層でデータを分割し、TCPセグメントを生み出す)。
- **MSS**(Maximum Segment Size): 一度に運べる量(TCPセグメントとして1回に送信できる最大データ量)。

### (復習)IPフラグメンテーション
MTU(一度に伝送できる最大サイズ)を超えるデータは**IPフラグメンテーション**で分割される。
例: MTU=1200バイトの経路に2800バイトを送りたい場合、ルータが1200/1200/400バイトに分割(フラグメント処理)する。各パケットには**識別子・フラグ・フラグメントオフセット**がつき、宛先PCは同一の識別子を持つパケットをフラグメントオフセットでくっつけて元に戻す。
ただしフラグメンテーションは全てのノードで分割/再構成処理が走るため効率が悪く、**現在ではほとんど使われていない**。

### TCPセグメンテーションとMSS
トランスポート層は**端末間の通信経路**、データリンク層は**機器間のリンク**。あらかじめ経路上のどのMTUにも引っかからない小さなサイズにTCPセグメントを分割しておけば、IPフラグメンテーションは起きない。

- MSSは**3ウェイハンドシェイクで決定**される。SYNのTCPヘッダのオプションに、自分が希望するMSSを書いて送る。
- 経路上のルータがオプションのMSSを見て、自分の方が小さければ**小さい方に書き換え**て転送する。
- 例: PC(MSS 1400) → ルータ(1200) → PC(MSS 1300)の場合、SYNでMSS 1400希望 → ルータで1200に書き換え → MSSは1200に決定。逆向きも1300希望 → 1200に書き換え → 1200に決定。

#### MSSとMTUの関係
- MSSはほとんどの場合**MTU − 40**で設定される。(**MTU: 1500 / MSS: 1460 が王道**。※1500はEthernetの最大許容サイズ)
- MTUはフレームのデータ部分(ヘッダとトレーラは含まない)で最大1500バイト。MSSはセグメントのデータ部分(ヘッダは含まない)で最大1460バイト。
- 差の40バイトは**IPヘッダ + TCPヘッダ**(最小で各20バイト)。

#### まとめ
- TCPセグメントとして1回に送信できる最大データ量を**MSS**(Maximum Segment Size)と言う。
- MSSは3ウェイハンドシェイクで決定される。経路上のMTUの最小値を元にして算出される。
- TCPにおいてデータをMSSのサイズに分割し、TCPセグメントを生み出すことを**TCPセグメンテーション**と言う。
- MSS値が適切に決められていればIPフラグメンテーションは起きない。

## シーケンス番号
分割したデータを受信側で**どうやって組み立てる**のか。
元のデータ全体(例: 100tのロボット)のうち「何番目から何t分」という**手がかり(札)**を各データに付けて送る。受信側はその手がかりを基に正しい順に再構成する。

この手がかりを**シーケンス番号**といい、送信側のTCPセグメンテーション(分割作業)の時に付与される。

### シーケンス番号の付け方
例: 送信データ10バイト、MSS 3バイトの場合。
1. 送信データの各バイトに連番を振る。最初に送りたいデータ(1バイト目)にはランダムの値(例: 100)を付ける(この初期値は3ウェイハンドシェイクで決定)。
2. MSSごとに分割する(3 / 3 / 3 / 2バイト)。
3. 分割単位の先頭の番号がそのセグメントのシーケンス番号になる(100 / 103 / 106 / 109)。

受信ホストはシーケンス番号の若い順に組み立てる。

> **次に受け取るデータのシーケンス番号 = 受け取ったデータのシーケンス番号 + 受け取ったデータのサイズ(長さ)**
> 例: 100 + 3 = 103

## シーケンス番号とACK番号の初期値
- **シーケンス番号**: 送信元⇒宛先に送信する、分割データが元データと比較してどの位置にあるかを示す番号。送信時に分割されたデータはこれを手がかりに再構成される。
- **確認応答番号(ACK番号)**: 宛先⇒送信元に返信する、次に受信したいデータのシーケンス番号を送信元に示す番号。送信元はこれを受け取ると「この直前までのデータは送信が成功した」と理解する。

どちらも**3ウェイハンドシェイクにおいては特殊な使い方**をされる。送信元・宛先は、内部にシーケンス番号とACK番号を保持している。

### 3ウェイハンドシェイクでの初期値の決まり方
(例: Aのシーケンス番号の初期値を1000、Bのを2000とする)
1. **A→B(SYN:1)**: 送信前準備として自分のシーケンス番号にランダムの値(1000)を設定し、SYNセグメントにセットして送信。
2. **B側の処理**: 受け取ったシーケンス番号(1000)を自身のACK番号に格納する。また接続要求(SYN:1)を送るため、シーケンス番号にランダムの値(2000)を設定。ACK番号には「**受け取ったシーケンス番号 + 1**」(1001)を設定する。
3. **B→A(ACK:1 / SYN:1)**: シーケンス番号2000、ACK番号1001で送信。
4. **A側の処理**: 受け取ったACK番号が自分が送ったシーケンス番号+1であることを確認し、接続承認を確認。受け取ったシーケンス番号(2000)を自身のACK番号に格納し、ACK番号を「受け取ったシーケンス番号 + 1」(2001)にする。シーケンス番号は1001。
5. **A→B(ACK:1)**: シーケンス番号1001、ACK番号2001で送信。Bは受け取ったACK番号が自分が送ったシーケンス番号+1であることを確認。

結果、A側はシーケンス番号1001、ACK番号2001、B側はシーケンス番号2001、ACK番号1001で後続のデータ通信に引き継がれる。
つまり3ウェイハンドシェイクは接続準備だけでなく、**シーケンス番号の初期値を決める**という役割も持つ。

#### まとめ
3ウェイハンドシェイクにおいてシーケンス番号とACK番号は以下のルールで決まる。(送信元をA、宛先をBとする)
1. A→B 接続要求(SYN:1)を送る際、シーケンス番号にランダムな値を設定。
2. B→A 接続要求に応える(ACK:1)際、ACK番号に「受け取ったシーケンス番号+1」を設定。接続要求(SYN:1)を送り返すため、シーケンス番号にはランダムな値を設定。
3. A→B 受け取ったACK番号が「送信したシーケンス番号+1」であることから接続承認を確認。接続要求に応える(ACK:1)ため、ACK番号に「受け取ったシーケンス番号+1」を設定。
4. 3ウェイハンドシェイクはその後で通信に用いるシーケンス番号の初期値を決定する役割も持つ。

## データの転送(順序制御)
例: 3ウェイハンドシェイクで決定した初期シーケンス番号 1001 / 初期ACK番号 2001、MSS 1400。送信データ3500バイト。

1. **TCPセグメンテーション**(MSS=1400)で 1400 / 1400 / 700バイトに分割。それぞれにシーケンス番号 **1001 / 2401 / 3801** が付く。(1001+1400=2401、2401+1400=3801)
2. 送信元は1つ目のセグメントのシーケンス番号に1001、ACK番号に2001(3ウェイハンドシェイクで決めた値)をセットして送信。
3. 宛先は受信すると**応答用セグメント**(データなし・サイズ0 / ACK:1)を生成する。
   - シーケンス番号: 受信したセグメントのACK番号をそのままセット(2001)
   - ACK番号: 受信したセグメントのシーケンス番号 + 受信データサイズ = 1001+1400 = **2401**(=次に送ってほしいシーケンス番号)
4. 送信元は応答を受け取って「送信成功」と判断し、ACK番号(2401)を見て次に送るデータを2401番のセグメントに決める。以降も同様に繰り返す。
5. 最後のセグメント(3801+700)に対する応答はACK番号4501となり、もう送るデータがないので終了。

**順序制御によるデータの転送におけるポイント**
- 送信元ホストは1番目に送るデータのシーケンス番号およびACK番号に、3ウェイハンドシェイクで決めた値をそれぞれ設定する。
- 宛先ホストはデータを受信すると確認応答用のセグメント(サイズ:0 / ACK:1)を送り返す。
- 送信元ホストも宛先ホストも、データを送り返す際は以下のルールでシーケンス番号とACK番号を設定する。
  - シーケンス番号: 送られてきたACK番号
  - ACK番号: 送られてきたシーケンス番号 + 送られてきたデータサイズ

## アクシデントへの対応(再送制御)
データが宛先に届けられない、または確認応答が迷子になって届かない、データが壊れていて確認応答を返さない、といったアクシデントが起こりうる。

- 確認応答を受信できない場合、送信元はそのデータの転送は失敗したとしてもう一度送りなおす。(**再送制御**)
- TCPでは「この時間待っても応答がなければ送信失敗とみなして再送する」という**再送タイマー**が設定される。この待機時間はネットワークによって異なり、具体的には3ウェイハンドシェイクの際に最適な時間を算出・設定する。
- 一定回数再送しても確認応答の受信がない場合、送信元は接続を強制終了する。

## 送信の効率化(ウィンドウ制御)
1セグメントごとに応答を待ってから送信していては通信が遅くなってしまう。

**ウィンドウ制御**: 応答を待たずに次々と送信するための技術。

### バッファとウィンドウサイズ
- 受信側にデータを一時保存できる領域(**バッファ**)を持たせることで通信速度をUPできる。受信側はバッファに溜まったデータを順次処理していく。
- **ウィンドウサイズ**は受信可能なバッファ領域のサイズ(TCPヘッダのウィンドウサイズフィールド)。初期ウィンドウサイズは**3ウェイハンドシェイクで送信元へと伝えられる**。

### スライディングウィンドウ
例: MSS 1000、バッファ(ウィンドウサイズ)3000バイトの場合。
- 送信元は3000バイト分(3セグメント)を確認応答なしで連続して送信できる。この送信可能な範囲が**ウィンドウ**。ウィンドウ外のデータは待機中。
- 送信したセグメントは確認応答待ちの状態になる。
- 確認応答が返ってきたセグメントは用済みになり、ウィンドウが1つ後ろにずれて、次のセグメントが送信可能になる。この動きを**スライディングウィンドウ**という。
- 確認応答待ちのセグメントは再送の可能性があるため、まだウィンドウ内に残しておく。

**ウィンドウ制御**: ウィンドウと呼ばれる送信可能なサイズ幅を管理しつつ、確認応答を待たずに次々とデータを送信する送信側の機能のことをウィンドウ制御と言う。

## 適切な送信量を調整(フロー制御/輻輳制御)
### フロー制御(流量制御)
受信側が高負荷でバッファが溢れそうな時、確認応答のウィンドウサイズを小さくして(例: 3000→1000)送信元に伝える。送信元はウィンドウを狭めて送信を抑制する。

**フロー制御(流量制御)**: 高負荷で処理がもたつきバッファが溢れそうな時などにウィンドウサイズを調整することで受信側が送信側の送信量をコントロールする機能。

(ウィンドウ制御は**送信側**の機能、フロー制御は**受信側**の機能。)

### 輻輳制御
受信側のバッファが5000あっても、他のコンピュータからのデータ受信などで実際の空きは2000しかない、ということがありうる。送信側はそれを知らないため、ウィンドウサイズ分(5000)を一気に送ると**輻輳**が発生しうる。

(復習: **輻輳**=大量データ通信などが原因でネットワークが混雑し、データ通信が困難になること。**ジッタ**=信号が想定より早くor遅く宛先に到着すること。データの変質・劣化を引き起こし、音声や映像の乱れなどを引き起こす。)

**輻輳制御**: ウィンドウサイズ分一気に送ってしまうと受信側の状況によっては処理しきれずに輻輳(ネットワーク上の混雑)を起こしてしまうことがあるため、慎重にデータを送信していく機能。

#### 輻輳ウィンドウと動き
- ウィンドウの中にさらに**輻輳ウィンドウ**という窓を設ける。輻輳ウィンドウは**送信側が**調整する、送信量調整用のウィンドウ。(普通のウィンドウサイズは受信側が伝える)
- 輻輳ウィンドウの外は、普通のウィンドウ内でも送信待ちになる。
- まず1セグメントだけ送って様子を見る。確認応答が1つ返ってきたら、**受け取った確認応答のセグメントのサイズ分だけ輻輳ウィンドウを拡張**する。
- 確認応答が2つ返ってきたら2セグメント分拡張して4セグメントを送信、というように 1→2→4→8 と倍々に増えていく。
- 輻輳ウィンドウはウィンドウサイズ(最大)を超えない。
- 輻輳が発生して確認応答が来ない(タイムアウト)場合は、輻輳ウィンドウを初期値(1セグメント)に戻してから送信を再開する。

#### スロースタート
輻輳制御の中心機能。最初は輻輳ウィンドウを1セグメント分で送信し、徐々に輻輳ウィンドウを広げていく(=送信量を増やしていく)ことで受信側の輻輳を防ぐ。輻輳ウィンドウは1→2→4→8と倍々に大きくなっていく。タイムアウトが起こると輻輳ウィンドウを初期値(1セグメント分)に戻してから送信を再開する。

## コネクションの終了
制御ビットの**FIN**を使い、3ウェイハンドシェイクと同様に以下の3ステップで行われる。(送信元をA、宛先をBとする)
1. A→B: 接続終了要求を伝えるため、**FIN:1**でセグメントを送信する。
2. B→A: 接続終了承認 & B→Aの接続終了要求を伝えるため、**ACK:1 / FIN:1**でセグメントを送り返す。
3. A→B: 接続終了承認を伝えるため、**ACK:1**でセグメントを更に送り返す。

これで双方向の接続終了となる。

## UDP
**UDP**(**User Datagram Protocol**)はTCPのようなコネクション・送信データの制御や管理といった概念が一切なく、指定されたポート番号に何もせずにデータを送るプロトコル。この通信方式は**コネクションレス型**と呼ばれる。

- UDPは信頼性を考慮しない**ベストエフォート型**の通信とも言える。信頼性が必要ならば上位のアプリケーション層で補うしかない。
- UDPヘッダは非常に単純な構造であり、TCPとは扱うデータの性質も異なるため、UDPで扱うデータの単位は**データグラム**と呼ばれる。
- **オーバーヘッド**(データ転送に付随して発生する処理負荷)が小さいため処理スピードが高速になる。そのため、IP電話やストリーミング、分割の不要な小さいデータの転送などで活用される。

### UDPヘッダ(データグラム)
UDPヘッダのフォーマット:
- 送信元ポート(16) / 宛先ポート(16)
- 長さ(16): UDPヘッダ+データのサイズ(バイト単位)
- チェックサム(16)

※何もしないと言っても、転送の過程でデータが壊れていないか程度のチェックは行う。

### (復習)TCP/IPにおけるPDU
TCP/IPにおいてもカプセル化/非カプセル化の概念は存在する。PDUはヘッダを付加したプロトコルによって名称が異なる。

| レイヤ | PDU |
| --- | --- |
| アプリケーション層 | メッセージ |
| トランスポート層(UDPの場合) | **UDPデータグラム** |
| インターネット層 | **パケット**(IPデータグラム) |
| リンク層 | **フレーム** |

## TCPとUDPの比較
| | TCP(信頼性を重視) | UDP(スピードを重視) |
| --- | --- | --- |
| 通信方式 | コネクション型(信頼性が高い) | コネクションレス型(信頼性が低い/ベストエフォート) |
| コネクション | 確立・終了を行う | 概念がない |
| 制御 | 通信の品質管理機能・回復機能を持ち、ウィンドウ制御や輻輳制御で柔軟な通信が可能 | 通信の制御を行わず、多少のデータ欠損も厭わない |
| オーバーヘッド | 大きい(高速性が低い) | 小さい(高速性が高い) |
| データの単位 | セグメント | データグラム |
| ヘッダ | シーケンス番号をはじめ、ヘッダで様々な情報を扱う | 非常に単純な構造 |
| 用途 | メールやファイル転送など、品質を求める通信 | IP電話やストリーミングなど、速度を求める通信 |
